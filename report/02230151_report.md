## 1. Objective

The aim of this practical was to stop assuming that a release is "safe" and to measure it instead. I deployed the Campus Notice Board API to a local kind cluster, built an availability monitor that sends one request every 0.5 seconds, and then released new versions using three strategies: Recreate, RollingUpdate and blue/green. For each release I counted failed requests and measured how long old and new versions were served at the same time. I also tested a broken release, a rollback, and a feature flag, to see which failures Kubernetes prevents by itself and which it does not.

## 4. Analysis

**A1. Ranking by failed requests.**
1. **Recreate: 8 failures** (`t5-recreate-summary.txt`).
2. **RollingUpdate, broken release, blue/green and flag change: 0 failures each** (a tie).

Recreate fails because it deletes all old Pods before any new Pod exists. In `t5-recreate-window.txt` the last 1.0.0 reply is at 18:40:58, the first FAIL is at 18:40:59 (`Connection refused`), the last FAIL is at 18:41:10 (`download timed out`) and the first 1.1.0 reply is at 18:41:12. During that gap the Service had no ready endpoints, and the new Pods also needed their 5-second warm-up before `/healthz` returned 200. RollingUpdate had zero failures because `maxUnavailable: 0` kept every old Pod serving until its replacement was ready (`t5-rolling-podwatch.txt` shows new Pods created and ready before old ones terminate). Blue/green had zero failures because both colours were already running and ready, and a switch only changes the Service selector (`t7-switch-marks.txt`, `t7-monitor-summary.txt`).

**A2. Why the broken release caused no failures.** The fields that protected the service were:
- `readinessProbe` on `/healthz`: the 1.2.0-broken Pod never returned 200, so it never became Ready and was never added to the Service endpoints (`t6-pods-during-failure.txt` shows it stuck at `0/1`).
- `maxUnavailable: 0` and `maxSurge: 1`: no old Pod was removed, so all three old Pods kept serving (the same file shows them `1/1 Running`).
- `progressDeadlineSeconds: 60`: after 60 s Kubernetes reported `Progressing=False`, reason `ProgressDeadlineExceeded` (`t6-deployment-conditions.txt`).
- `livenessProbe` on `/version`, not `/healthz`: the broken Pod was not killed and restarted in a loop.
- `imagePullPolicy: Never`: the kubelet never tried a registry.

Predictions if each field had been left at its default:
- `progressDeadlineSeconds` (default 600 s): the monitor result would be the same, but the failure would only be reported after 10 minutes.
- `maxUnavailable` / `maxSurge` (default 25% each): with 3 replicas these round to 0 unavailable and 1 surge, so the monitor would record the same result.
- No `readinessProbe` (the real risk): the broken Pod would count as Ready as soon as its container started and would receive about a quarter of the traffic. Because the monitor calls `/version`, which still works in the broken image, I would expect `1.2.0-broken` responses in the version counts and the rollout reported as successful, with possibly a few connection failures in the first moments of startup. The broken `/healthz` would never have been noticed.

**A3. RollingUpdate versus blue/green.**

| Axis | RollingUpdate | Blue/green |
|---|---|---|
| Mixed-version window | 36 s (`t5-rolling-window.txt`) | ≈ 0 s: the version changes at the Service switch (`t7-monitor.log`) |
| Peak resources vs quota | 4 app Pods ≈ 400m CPU requested | 6 app Pods + monitor: 620m of 1 CPU, 1250m of 2 CPU limits, 7 of 15 Pods (`t7-quota-both-colours.txt`) |
| Time to roll back | A new rolling update (`kubectl rollout undo`), taking about as long as a normal release | One Service edit; switch 2 was a single apply (`t7-switch-marks.txt`) |

Blue/green gives a near-instant switch and rollback at the price of running twice the Pods, which used 62% of the CPU request quota.

**A4. When Recreate is correct.** Recreate is right when two versions must never run at the same time. For example, a version that migrates a database schema in a way the old version cannot read, or an application that holds an exclusive lock or a single read-write volume. A short, planned outage is then better than two versions corrupting the same data.

**A5. What the feature flag allowed and what it did not avoid.** The flag let me change the behaviour (pinned notices listed first) by editing a ConfigMap, without building a new image: the 1.1.0 image was unchanged (`t8-notices-before.txt`, `t8-notices-after.txt`). It did not avoid a Pod restart. The running green Pods still reported `FEATURE_PINNED=false` after the ConfigMap changed to `true` (`t8-pods-observe-flag.txt`), because an environment variable is fixed when the container starts. I still needed a declarative change to the Pod template to roll the Pods, which completed with 0 failed requests (`t8-monitor-summary.txt`).

## 5. Reflection

**Error met.** `kind load docker-image busybox:1.36 --name cte412-02230151` failed with:

```
ERROR: failed to load image: command "docker exec --privileged -i cte412-02230151-control-plane ctr --namespace=k8s.io images import ... -" failed with error: exit status 1
Command Output: ctr: content digest sha256:71b0cbca...: not found
```

My own images had loaded fine, so the problem was specific to `busybox`. The message says the node could not find a content blob. I reasoned that the busybox image is multi-platform, and Docker Desktop's image store did not hold every platform's content for kind to import. Exporting only the platform I needed with `docker save --platform linux/amd64 busybox:1.36 -o busybox.tar` and loading it with `kind load image-archive` worked, and `crictl images` on the worker then listed `busybox 1.36`. Two smaller problems were solved the same way: `bash` pointed to a WSL with no Linux installed (fixed by calling Git's `bash.exe`), and `kubectl diff` needed a `diff` program that Windows does not have (fixed by adding Git's `usr\bin` to PATH).

**Still unclear.** During the RollingUpdate release, `t5-rolling-podwatch.txt` shows the old Pods ending in status `Error` before being deleted, rather than a clean termination. I think this is because the Python server does not handle SIGTERM, so Kubernetes waited out the grace period and killed it. I did not confirm this, for example by checking the Pod's exit code or testing a signal handler, and it did not cause failed requests because the Pod had already been removed from the Service.
